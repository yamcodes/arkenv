This guide walks you through wiring ArkEnv into a TanStack Start app.
You'll validate environment variables before the server is ready, read
server secrets inside `createServerFn`, and keep those secrets out of
the browser bundle.

The complete working example lives in
[`examples/with-tanstack-start`](https://github.com/yamcodes/arkenv/tree/v1/examples/with-tanstack-start).
For Rsbuild and the full reference, see the
[TanStack Start framework guide](/docs/frameworks/tanstack-start).

## What you'll learn

1. Scaffolding ArkEnv with the TanStack CLI add-on or `arkenv init`
2. Registering `@arkenv/vite-plugin` next to TanStack Start and React
3. Defining a single `src/env.ts` schema with public `VITE_*` keys and
   server-only secrets
4. Reading validated env from `createServerFn` and client components
5. Catching accidental client access to server secrets at runtime

## Prerequisites

- A TanStack Start app on Vite (or willingness to scaffold a new one)
- Basic familiarity with React and TypeScript
- Node.js and a package manager (`npm`, `pnpm`, `yarn`, or `bun`)

## Nice to know

- How TanStack Start's `createServerFn` and route loaders work
- That Vite builds separate SSR and client module graphs

## Setting up ArkEnv

### Create a new project

Generate a TanStack Start app with ArkEnv already wired in:

```package-install
npx @tanstack/cli create my-app --add-ons https://arkenv.js.org/tanstack/info.json
```

When the CLI runs, it asks a few setup questions — including which
validator engine to use (ArkType, Zod, or Valibot) and whether to
include the `/demo/arkenv` route. You can accept the defaults or pick
what fits your project.

The add-on installs the runtime packages, registers the Vite plugin in
`vite.config.ts`, writes `src/env.ts`, and pre-populates declared keys
in `.env.example`.

### Existing projects

If you already have a TanStack Start app on Vite, add ArkEnv with either
the TanStack CLI add-on or the ArkEnv CLI:

```package-install
npx @tanstack/cli add https://arkenv.js.org/tanstack/info.json
```

```package-install
npx arkenv init
```

`arkenv init` detects `@tanstack/react-start` (or `@tanstack/start`) and
installs `@arkenv/vite-plugin` the same way it does for plain Vite
projects.

Install dependencies if the CLI did not already, then start your usual
dev script (`npm run dev`, `pnpm dev`, and so on). You should land on
the Start welcome page (or your existing app) with ArkEnv validating
`src/env.ts` as Vite comes up.

## Understanding the Vite config

At this point your `vite.config.ts` should register TanStack Start,
React, and ArkEnv in that order:

```ts title="vite.config.ts" twoslash
// @noErrors
import { tanstackStart } from "@tanstack/react-start/plugin/vite";
import viteReact from "@vitejs/plugin-react";
import arkenvVitePlugin from "@arkenv/vite-plugin";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [
    tanstackStart({ srcDirectory: "src" }),
    // React's Vite plugin must come after Start's plugin
    viteReact(),
    arkenvVitePlugin(),
  ],
});
```

In this config:

- `tanstackStart()` owns Start's SSR and routing pipeline.
- `viteReact()` must come **after** Start. Without it, Vite cannot
  resolve `/@react-refresh`, SSR still renders, and client hydration
  fails so handlers never attach.
- `arkenvVitePlugin()` discovers and validates `src/env.ts` during Vite
  config resolution. Missing or invalid values abort the dev server or
  production build before it is ready.

If you aren't using ArkType, import the plugin from
`@arkenv/vite-plugin/standard` instead.

## Defining your schema

ArkEnv uses a single `src/env.ts` file as the contract for every
environment variable in the app.

```ts title="src/env.ts" twoslash
import arkenv from "@arkenv/core";

export const env = arkenv({
  DATABASE_URL: "string",
  PORT: "number.port = 3000",
  VITE_API_URL: "string = 'https://api.example.com'",
  NODE_ENV: "'development' | 'production' | 'test' = 'development'",
});
```

A few rules of thumb:

- Prefix public variables with `VITE_` so the Vite plugin can inline
  them into the client bundle.
- Leave secrets un-prefixed so they stay on the server graph.
- Prefer `@arkenv/core` with ArkType. Use `@arkenv/standard` if you
  already validate with Zod or Valibot.

Import `{ env }` from this module everywhere. Reading `import.meta.env`
or `process.env` directly skips ArkEnv's types, coercion, and leak
protection.

## Reading variables: createServerFn vs. UI components

TanStack Start routes often mix server loaders, server functions, and
React UI in the same file. ArkEnv keeps each layer on the right side of
the boundary.

```tsx title="src/routes/index.tsx" twoslash
// @noErrors
// @filename: env.ts
import arkenv from "@arkenv/core";
export const env = arkenv({
  DATABASE_URL: "string",
  VITE_API_URL: "string = 'https://api.example.com'",
  NODE_ENV: "'development' | 'production' | 'test' = 'development'",
});

// @filename: index.tsx
// ---cut---
import { createFileRoute } from "@tanstack/react-router";
import { createServerFn } from "@tanstack/react-start";
import { env } from "../env";

// Runs exclusively on the server
const getDatabaseHost = createServerFn({ method: "GET" }).handler(() => {
  const url = new URL(env.DATABASE_URL); // validated at boot
  return url.host; // safe to return to the client
});

export const Route = createFileRoute("/")({
  component: HomePage,
  loader: () => getDatabaseHost(),
});

function HomePage() {
  const dbHost = Route.useLoaderData();

  return (
    <main>
      {/* Public key inlined into the client bundle */}
      <h1>API: {env.VITE_API_URL}</h1>
      <p>Connected to: {dbHost}</p>
    </main>
  );
}
```

In this code:

- `getDatabaseHost` reads `DATABASE_URL` inside a `createServerFn`
  handler. That handler runs on the server graph, where `env.ts`
  executes the real validation runtime against `process.env`.
- The loader returns only `url.host` to the client — the secret itself
  never crosses the wire.
- `HomePage` reads `env.VITE_API_URL` in the component. The plugin
  rewrites the client module so public values are inlined as coerced
  literals.

## What happens when client code accesses a server secret?

If someone accidentally references a server key in client-rendered code:

```tsx twoslash
// @noErrors
// @filename: env.ts
import arkenv from "@arkenv/core";
export const env = arkenv({
  DATABASE_URL: "string",
});

// @filename: index.tsx
// ---cut---
import { env } from "../env";

function ClientWidget() {
  return <div>{env.DATABASE_URL}</div>;
}
```

ArkEnv does not fail silently or ship the secret into the client
bundle. The transformed client getter throws immediately:

> `Do not access server-only key 'DATABASE_URL' on the client since it will leak sensitive data (prevented by ArkEnv)`

That surfaces the leak during development (and in tests) before it
reaches production.

## How the two module graphs fit together

TanStack Start builds on Vite, so you get two module graphs:

1. **Server graph (SSR):** `src/env.ts` runs the real `@arkenv/core` (or
   `@arkenv/standard`) runtime at boot and validates your process
   environment before requests are served. `createServerFn` handlers
   live here.
2. **Client graph:** `@arkenv/vite-plugin` transforms `src/env.ts`
   during the client build. Public `VITE_*` keys become typed literals.
   Server-only keys become throwing getters. The validation engine
   itself never ships to the browser.

Like Vite, TanStack Start loads `.env*` files in development. In
production, the environment comes from the process that starts your
server, so containers must inject variables before boot.
