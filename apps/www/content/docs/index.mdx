## What is ArkEnv?

ArkEnv is a typesafe environment variable validation library for JavaScript
and TypeScript. You declare a schema once, `arkenv()` validates the
process against that schema before application code runs, and TypeScript
infers the types from the same declaration.

This page shows why `process.env` is a weak contract, how ArkEnv's typed
`env` object replaces it, and where to go next in these docs.

## The `process.env` problem

In JavaScript and TypeScript apps, environment variables are the primary
way to configure a process. The problem is that TypeScript only types
those values as `string | undefined`, so anything beyond that is your responsibility - including checking the type and making sure that the value is even defined.

Let's see how this gets messy if not done carefully. Can you spot the
problem with this code?

```ini title=".env"
DEBUG=false
```

```ts title="./server.ts" twoslash
const debug = process.env.DEBUG;
//    ^?

if (debug) {
  console.log("verbose logging enabled");
}
```

**Does it log the message?**

Spoiler alert: yes, it does. `process.env.DEBUG` is the string `"false"`,
not the boolean `false`. In JavaScript, a non-empty string is truthy, so
`if (debug)` runs even though you turned logging off.

A more seasoned developer might know to check `debug !== "false"`. The
next developer might not. They might expect `debug` to be a boolean.

Soon you start parsing environment variables by hand. You might also assign a
default. To make the code safe, you add a type check and a null check.
At that point, it looks like this:

```ts title="./server.ts"
const raw = process.env.DEBUG;
const debug: boolean = raw == null ? false : raw === "true";

if (debug) {
  console.log("verbose logging enabled");
}
```

That becomes a maintenance burden as soon as usage scales: across
multiple files, for
[client vs. server](/docs/validating-environment-variables/client-vs-server),
and across apps.

## The `env` solution

ArkEnv solves that scaling problem. `arkenv()` parses your values against
a schema you define in a single `env.ts` file, so you don't handle the
loose `process.env` object in application code.

The same `if`, after ArkEnv, looks like this:

```ts title="./env.ts" twoslash
import arkenv from "@arkenv/core";

export const env = arkenv({
  DEBUG: "boolean = false",
});
```

```ts title="./server.ts" twoslash
// @filename: env.ts
import arkenv from "@arkenv/core";

export const env = arkenv({
  DEBUG: "boolean = false",
});

// @filename: server.ts
// ---cut---
import { env } from "./env";

const debug = env.DEBUG;
//    ^?

if (debug) {
  console.log("verbose logging enabled");
}
```

Here `debug` is `boolean` by definition. ArkEnv's
[coercion](/docs/core-concepts/coercion) turns the string `"false"` into
`false` by that same definition, so the `if` does not run and verbose
logging stays off.

In a full-stack app, you must keep secrets off the client. The
[Next.js](/docs/guides/frameworks/nextjs),
[Nuxt](/docs/guides/frameworks/nuxt),
[Vite](/docs/guides/frameworks/vite), and
[Bun](/docs/guides/frameworks/bun) packages enforce that split so server
values stay out of the client graph. See
[Client vs. server](/docs/validating-environment-variables/client-vs-server).

If you already use a Standard Schema validator for forms or API data,
run `pnpm dlx arkenv@latest init` to add ArkEnv to an existing project.
You can keep [Zod](https://zod.dev), [Valibot](https://valibot.dev), or
any [Standard Schema](https://standardschema.dev/) validator with
[`@arkenv/standard`](/docs/reference/standard), or use
[ArkType](https://arktype.io) with [`@arkenv/core`](/docs/reference/core),
which ArkEnv was designed around. See
[Add to an existing repository](/docs/getting-started/add-to-existing-repository).
