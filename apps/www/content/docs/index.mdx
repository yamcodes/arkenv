## What is ArkEnv?

ArkEnv is a typesafe environment variable validation library for TypeScript. You declare a schema once, `arkenv()` validates the
process against that schema before application code runs, and TypeScript
infers the types from the same declaration.

This page shows why `process.env` is a weak contract, how ArkEnv's typed
`env` object replaces it, and where to go next in these docs.

## The `process.env` problem

Environment variables are available via the `process.env` (or `import.meta.env`) object. This object is loosely typed - all values are `string | undefined`.

The problem with a loosely typed object is that you have **no** runtime guarantee about a given value: Is it correct type? Does it match our constraints? Does the value even exist?

```ini title=".env"
PORT=3000
DEBUG=false
```

```ts title="./server.ts" twoslash
const port = process.env.PORT;
const debug = process.env.DEBUG;
//    ^?

if (debug) {
  console.log("verbose logging enabled");
}

console.log(`listening on ${port}`);
```

In this example, `port` can be anything (even a negative number), and `verbose logging enabled` is logged to the console, even though we set `DEBUG=false` in our `.env` file. We can fix this by manually parsing the value:

```ts title="./server.ts" twoslash
const port = Number(process.env.PORT ?? "3000"); // [!code ++]
if (port < 0 || port > 65535) { // [!code ++]
  throw new Error("PORT must be between 0 and 65535"); // [!code ++]
} // [!code ++]
const debug = process.env.DEBUG === "true"; // [!code ++]

if (debug) {
  console.log("verbose logging enabled");
}

console.log(`listening on ${port}`);
```

Now the process correctly skips the `verbose logging enabled` message, matching the `DEBUG=false` in our `.env` file.

## The `env` solution

**ArkEnv solves the environment variable scaling problem.** Declare a
schema in `env.ts`; `arkenv()` validates against it so application code never
touches loose `process.env`:

```ts title="./env.ts" twoslash
import arkenv from "@arkenv/core";

export const env = arkenv({
  PORT: "number.port = 3000",
  DEBUG: "boolean = false",
});
```

The same `if` as above, after ArkEnv:

```ts title="./server.ts" twoslash
// @filename: env.ts
import arkenv from "@arkenv/core";

export const env = arkenv({
  PORT: "number.port = 3000",
  DEBUG: "boolean = false",
});

// @filename: server.ts
// ---cut---
import { env } from "./env";

const port = env.PORT;
const debug = env.DEBUG;
//    ^?

if (debug) {
  console.log("verbose logging enabled");
}

console.log(`listening on ${port}`);
```

Everything works like our manual solution, but the parsing logic is written declaratively in a single file. This makes the code simpler and more maintainable.

In a full-stack app, we **must keep secrets off the client**. The Next.js,
Nuxt, Vite, and Bun packages enforce that split. See
[Client vs. server](/docs/core-concepts/client-vs-server).

ArkEnv uses ArkType by default. However, **it works with Zod, Valibot, and any other [standard schema](https://standardschema.dev/)**. See the [Zod](/docs/validators/zod) guide for one such example.
