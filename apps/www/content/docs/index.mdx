## What is ArkEnv?

ArkEnv is a typesafe environment variable validation library for JavaScript
and TypeScript. You declare a schema once, `arkenv()` validates the
process against that schema before application code runs, and TypeScript
infers the types from the same declaration.

This page shows why `process.env` is a weak contract, how ArkEnv's typed `env`
object replaces it, and where to go next in these docs.

## The `process.env` problem

In the JS community, environment variables are the primary way to configure an app. The problem is that TypeScript only defines these variables as `string | undefined`, so anything beyond that is up to you to handle manually. This includes checking if the value is a certain type or even defined at all.

Let's see how this can get messy if not handled carefully. Can you spot the problem with this code?

```ini title=".env"
DEBUG=false
```

```ts title="./server.ts" twoslash
const debug = process.env.DEBUG;
//    ^?

if (debug) {
  console.log("verbose logging enabled");
}
```

Does it log the message?

Spoiler alert: yes, it does! This is because `process.env.DEBUG` is the string `"false"`, not the boolean `false`. In JavaScript, a non-empty string is truthy, so the `if (debug)` branch runs even though you explicitly turned it off!

Now, a more seasoned developer might know to check `debug !== "false"`. But the next developer might not, they might expect `debug` to be a boolean.

Soon you start parsing environment variable manually (with `Boolean(process.env.DEBUG)` in this case). You might also think of assigning a default value.

And to make this code safe, you want to add a type check and a null check. At this point, your code looks like this:

This becomes a maintaince burden as soon as your environment variabels usage starts scaling (over multiple files, for [client vs. server](/docs/validating-environment-variables/client-vs-server), and across apps).

## The `env` solution

ArkEnv solves your environment variable scaling problem. `arkenv()` parses your values against a schema you define in a single `env.ts` file, meaning you don't have to handle the loose `process.env` object in application code.

The same `if`, after ArkEnv, looks like this:

```ts title="./env.ts" twoslash
import arkenv from "@arkenv/core";

export const env = arkenv({
  DEBUG: "boolean = false",
});
```

```ts title="./server.ts" twoslash
// @filename: env.ts
import arkenv from "@arkenv/core";

export const env = arkenv({
  DEBUG: "boolean = false",
});

// @filename: server.ts
// ---cut---
import { env } from "./env";

const debug = env.DEBUG;
//    ^?

if (debug) {
  console.log("verbose logging enabled");
}
```

Here `debug` is `boolean` by definition. ArkEnv's [coercion](/docs/core-concepts/coercion) turns the string `"false"` into
`false` by that same definition, so the `if` does not run and verbose logging stays off.

Additionally, in a full-stack app, you MUST keep secrets off the client. ArkEnv's [security model](/docs/core-concepts/security) ensures this by default. The
[Next.js](/docs/guides/frameworks/nextjs),
[Nuxt](/docs/guides/frameworks/nuxt),
[Vite](/docs/guides/frameworks/vite), and
[Bun](/docs/guides/frameworks/bun) packages enforce that split so server
values stay out of the client graph.

There's a fair chance you already use a Standard Schema validator to handle dynamic data in your app (forms, API requests, etc.). In this case, you can **run `npx arkenv@latest init` to add ArkEnv to your existing project and get started right away**. You can use ArkEnv with any Standard Schema validator, like Zod, Valibot or Typia. Of course, you can also use ArkType, which ArkEnv was designed around in the first place.
